## Build System Overview

NetForge is a pure-Python package built and distributed using **PEP 517/518** standards. There are no Makefiles, Dockerfiles, shell build scripts, or CI pipelines in the repository — the entire build and packaging surface is defined declaratively in `pyproject.toml`.

## What System Is Used

- **Build backend**: `setuptools.build_meta` (requires `setuptools>=68`, `wheel`). This is the modern PEP 517 entry point that lets `pip install .` or `python -m build` produce standard sdist/wheel artifacts.
- **Versioning**: Single source of truth at `[project] version = "0.2.0"` in `pyproject.toml`. No separate version file; the version is read directly by the build backend.
- **Python requirement**: `requires-python = ">=3.10"` declared in the project table.
- **CLI entry point**: Exposed as a console script named `netforge` bound to `cli:app` via `[project.scripts]`.
- **Dependency management**: Two layers:
  - Declarative runtime dependencies declared in `pyproject.toml` under `[project].dependencies` (`typer`, `rich`, `pydantic`, `psutil`).
  - A pinned `requirements.txt` listing all transitive resolved dependencies (likely generated by `pip freeze`), used for reproducible environments but not consumed by the build system itself.
- **Optional dev dependencies**: Declared under `[project.optional-dependencies] dev = ["pytest>=8.0"]`, installable via `pip install -e .[dev]`.

## Key Files

- `pyproject.toml` — single source of truth for build metadata, dependencies, package discovery, CLI entry points, and pytest configuration.
- `requirements.txt` — fully pinned dependency lockfile (used for environment reproducibility).
- `cli.py` — top-level module exposed as the `netforge` console script.
- `netforge.egg-info/` — generated artifact from an editable install; contains `PKG-INFO`, `SOURCES.txt`, `entry_points.txt`, `requires.txt`, `top_level.txt`.
- `tests/` — pytest test suite configured via `[tool.pytest.ini_options]` with `testpaths = ["tests"]` and `pythonpath = ["."]` so tests can import sibling packages without installation.

## Architecture and Conventions

- **Package layout**: The root directory is both the Python package root and the project root. Packages are discovered automatically via `[tool.setuptools.packages.find]` with an explicit include list: `core*`, `diagnostics*`, `analysis*`, `ingest*`, `collectors*`, `storage*`. The `agent`, `controller`, and `cli` modules are NOT included in the installed package — they are only available when running the repo directly (editable install) or via the `netforge` console script which imports `cli:app`.
- **Single-package distribution**: The project builds one wheel named `netforge` containing the core diagnostic library plus optional subpackages. Agent and controller services are not packaged as separate distributions; they are run directly from source.
- **Testing convention**: All tests live under `tests/` and use pytest. Test discovery is configured centrally in `pyproject.toml`; there is no `pytest.ini` or `setup.cfg` override.
- **No virtualenv in VCS**: A local `venv/` directory exists but is excluded from the build. The `.gitignore` includes `.pytest_cache/`.

## Conventions and Constraints

- **No Makefile / shell scripts**: Build, packaging, and testing are driven entirely through `pip`/`setuptools` and `pytest`. There are no custom build steps, pre/post hooks, or compilation phases.
- **No containerization**: No `Dockerfile`, `docker-compose.yml`, or similar files exist in the repository.
- **No CI/CD**: No `.github/workflows/`, `.gitlab-ci.yml`, or other CI configuration is present.
- **Editable installs preferred**: The presence of `netforge.egg-info/` indicates development uses `pip install -e .` rather than building wheels during development.
- **Dependency pinning strategy**: Runtime deps are specified with minimum versions in `pyproject.toml` (e.g., `pydantic>=2.13.5`), while `requirements.txt` pins exact versions of all transitive dependencies — suggesting a workflow where `requirements.txt` is regenerated from a locked environment and used for deployment/reproducibility.
- **Test isolation**: Pytest is configured with `pythonpath = ["."]` so tests import the in-tree packages directly, avoiding the need to install the package before running tests.
