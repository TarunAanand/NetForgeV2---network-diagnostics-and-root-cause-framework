## What system/approach is used

NetForge uses a standard Python dependency management setup built on **PEP 517/621** with `setuptools` as the build backend. Runtime dependencies are declared in two places:

- **`pyproject.toml`** — the canonical source of truth for installable package metadata, runtime dependencies, optional dev dependencies, entry points, and packaging configuration.
- **`requirements.txt`** — a pinned flat list of all transitive dependencies (including indirect ones like `annotated-types`, `markdown-it-py`, `Pygments`, etc.) used for environment provisioning.

There is no lockfile (`requirements.lock`, `poetry.lock`, `uv.lock`) and no vendored third-party code under `vendor/`. The project also generates an `netforge.egg-info` directory produced by `pip`/`setuptools` during installation, which mirrors the declared dependencies.

## Key files and packages

- **`pyproject.toml`** — declares `requires-python = ">=3.10"`, runtime dependencies (`typer`, `rich`, `pydantic`, `psutil`), optional `[dev]` extras (`pytest>=8.0`), the `netforge` CLI entry point (`cli:app`), and the package discovery scope (`core*`, `diagnostics*`, `analysis*`, `ingest*`, `collectors*`, `storage*`).
- **`requirements.txt`** — fully pinned versions of every dependency actually present in the active environment, including transitive deps pulled in by `pydantic` and `rich`.
- **`netforge.egg-info/requires.txt`** — auto-generated by setuptools/pip; mirrors the `dependencies` and `[project.optional-dependencies]` sections from `pyproject.toml`.
- **`venv/`** — a local virtual environment directory exists at the repo root, indicating per-project isolated installs rather than global user-site installs.

## Architecture and conventions

- **Single source of truth**: `pyproject.toml` is the authoritative manifest. `requirements.txt` appears to be generated or manually synchronized to capture exact resolved versions (e.g., `pydantic==2.13.5`, `rich==15.0.0`, `typer==0.27.2`, `psutil==7.2.2`).
- **Minimal runtime surface**: Only four direct runtime dependencies are declared (`typer`, `rich`, `pydantic`, `psutil`); everything else (CLI formatting, markdown rendering, type inspection) is pulled transitively through those libraries.
- **Optional dev tooling**: Testing is isolated behind the `dev` extra (`pip install .[dev]`), keeping production installs free of `pytest`.
- **No private registry or vendoring**: There is no `setup.cfg` index URL, no `pip.conf`/`pip.ini`, no `--extra-index-url`, no `PYPI_URL`, no `GOFLAGS=-mod=vendor`, and no vendored packages. All packages resolve from the default PyPI.
- **Build system**: Uses modern PEP 517 with `setuptools.build_meta` and `wheel`; no custom build hooks or C extensions.

## Conventions and constraints

Observed patterns (descriptive):
- Dependencies use **minimum version pins** (`>=X.Y.Z`) in `pyproject.toml`, allowing newer compatible releases while constraining the minimum.
- `requirements.txt` uses **exact pins** (`==`), likely produced by `pip freeze` or a similar snapshot tool, to reproduce an environment.
- The project targets **Python ≥ 3.10**, enforced by `requires-python` in `pyproject.toml`.
- Package discovery is explicit via `[tool.setuptools.packages.find].include`, limiting distribution to the six top-level namespaces listed.
- The CLI entry point `netforge` maps to `cli:app`, making the framework installable as a console script.

Constraints not observed in this repository:
- No lockfile format is used; there is no mechanism documented or configured to pin transitive dependencies deterministically across machines.
- No private/internal package registry is configured.
- No vendoring strategy exists; third-party code is never checked into the repository outside `venv/` and `netforge.egg-info/`.
- No CI step was found that enforces dependency freshness, vulnerability scanning, or lockfile synchronization.
